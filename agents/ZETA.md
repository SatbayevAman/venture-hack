# Агент Дзета · Аккаунты, классы, безопасность

Ты — агент **Дзета**. Сейчас приложение — демо для одного учителя:
- входа нет;
- класс один;
- ключ API вводится в боковой панели;
- персональные данные защищены только тем, что они синтетические.

Твоё направление превращает MVP в то, что можно поставить в школу: роли, изоляция классов, согласие на обработку данных, журнал действий, удаление данных, выгрузка итогов. Это критерий «практическая реализуемость» и правило жюри при равенстве баллов — «техническая реализация, архитектура и безопасность» (п. 6.4 Положения).

**Кратко**

- **Результат:**
  - этап A — вход и роли (учитель, ученик, администратор); учитель видит только свои классы; согласие и журнал действий; удаление данных ученика; выгрузка итогов;
  - этап B — классы, импорт списка учеников, создание заданий учителем;
  - этап C — PostgreSQL.
- **Объём:** этап A — примерно 3–4 часа, этап B — 3–4 часа, этап C — только после слияния остальных направлений.
- **Зависимости:** этапы A и B — нет; этап C — после слияния всех остальных веток.

### Проект

**Портрет ученика** — MVP команды на хакатоне VENTUREHACK 2026, трек «Образование». Веб-приложение для учителя математики на Streamlit. Автопроверка домашних работ по алгебре 7–9 классов (SymPy) записывает в *журнал наблюдений* ошибки, способы решения и привычки ученика. Из журнала и комментариев учителя собирается *портрет* «где слаб и как работать» и *карта класса*. Интерфейс на русском и казахском.

Репозиторий: https://github.com/SatbayevAman/venture-hack. Подробности — в `README.md`.

### Принципы — нарушать нельзя

1. **Модель только на входе и на выходе.** Языковая модель распознаёт почерк, размечает свободный текст учителя и переформулирует готовые советы. Всё, что считает и решает, — обычный код, поэтому любой вывод воспроизводим.
2. **Только словарь тегов.** Выводы об ученике — только коды из `core/tags.py`. Неизвестный тег `db.add_observation` превращает в `other` или `teacher_other`. Новый вид вывода — это новый тег в словаре: название, совет учителю и совет ученику на `ru` и `kk`.
3. **Доказательство у каждого вывода:** работа, задача, строка, цитата. Меньше 3 случаев — пометка «мало данных» вместо вывода.
4. **Тон.** Описываем действия («в 4 работах из 6 нет проверки»), а не характер. Наводящий вопрос никогда не называет ответ. Версия для ученика — мягкая.
5. **Приватность.** Псевдонимы вместо имён. Фото не сохраняются — только строки текста. Синтетические данные везде подписаны как синтетические.
6. **Без ключа API всё работает.** Новая функция с языковой моделью обязана иметь офлайн-путь или аккуратно отключаться с объяснением.
7. **Два языка.** Каждая строка интерфейса — через `L("рус", "қаз")`, в словарях — поля `ru` и `kk`. Все новые казахские тексты перечисли в отчёте: их вычитает носитель языка.

### База и журнал

Таблицы в `core/db.py`: `students`, `assignments`, `problems`, `submissions` (`source`: `synthetic` или `live`), `attempts`, `steps`, **`observations`**, `teacher_comments`, `tags`. Портрет нигде не хранится: он каждый раз считается заново из `observations`.

Одна строка журнала — это контракт между проверкой и портретом:

```json
{"student_id": 1, "submission_id": 42, "problem_id": 27, "line_no": 1, "kind": "error",
 "tag": "lost_root", "skill": "quadratic", "evidence": "x² = 7x  →  x = 7",
 "detail": {"f": "x", "division": true}, "source": "auto", "confidence": 0.9}
```

Поля и смысл существующих значений не меняются. Новые значения `source` допустимы (например, `practice`): `portrait.build` учитывает только `auto` и `teacher`, поэтому числа портрета от них не меняются.

### Как работать параллельно с другими агентами

1. Ветка `agent/<имя>` от свежего `main`, небольшие осмысленные коммиты. Порядок: этап A целиком → все тесты проходят → PR; этап B — следующими коммитами после него.
2. Свой код — в своих новых файлах (см. раздел «Границы»). В общих файлах — только точечные вставки в указанных местах. Не переформатируй, не переименовывай и не переноси чужой код.
3. Сигнатуры существующих функций не меняй. Можно добавить необязательный параметр, если при значении по умолчанию поведение прежнее.
4. Новые таблицы — не в `db.SCHEMA`, а в своём модуле: константа `SCHEMA` и функция `ensure_schema(conn)` с `CREATE TABLE IF NOT EXISTS`. Твой код вызывает её перед обращением к таблице. Существующие таблицы не меняй, никаких `ALTER TABLE`.
5. Страница интерфейса — модуль `ui/<имя>.py` с функцией `render(...)`. `ui/__init__.py` — пустой файл; если его ещё нет, создай пустым. В `app.py` добавляются только импорт, ключ в `PAGES`, подпись в `PAGE_NAMES` и запись в словаре страниц в последней строке.
6. Новые зависимости — только если без них никак: строкой в `requirements.txt` с комментарием и с объяснением в отчёте. Python 3.9+: `from __future__ import annotations`, без `match`.
7. Тесты — в `tests/test_<имя>.py`, без сети и без ключа API (языковую модель подменяй через `monkeypatch`). Существующие тесты не правь.
8. `README.md` не трогай. Описание своей работы — в `docs/<имя>.md`; ссылку в README добавит человек при слиянии.
9. Конфликты при слиянии ожидаются только в местах регистрации: импорты в начале `app.py`, `PAGES`, `PAGE_NAMES`, словарь страниц в последней строке `app.py`, блоки словаря `TAGS`. Они аддитивны: оставляй обе стороны.

## Этап A — обязательный минимум

### Z1. Пользователи — `core/auth.py`, без Streamlit

```sql
CREATE TABLE IF NOT EXISTS users (
    id INTEGER PRIMARY KEY,
    login TEXT NOT NULL UNIQUE,
    display_name TEXT NOT NULL,
    role TEXT NOT NULL CHECK (role IN ('admin', 'teacher', 'student')),
    password_hash TEXT NOT NULL,
    salt TEXT NOT NULL,
    student_id INTEGER,              -- для роли student
    disabled INTEGER NOT NULL DEFAULT 0,
    created_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS teacher_classes (
    user_id INTEGER NOT NULL,
    class_name TEXT NOT NULL,
    PRIMARY KEY (user_id, class_name)
);
```

- `hash_password(password, salt=None)` — `hashlib.pbkdf2_hmac("sha256", …, 200_000)`, соль `secrets.token_hex(16)`; сравнение — `hmac.compare_digest`.
- `create_user(...)`.
- `authenticate(conn, login, password) -> user | None`: пустой пароль и `disabled` — отказ. Сообщение об ошибке одинаковое для «нет пользователя» и «неверный пароль».
- `visible_student_ids(conn, user) -> set[int] | None`:
  - `None` — все ученики (администратор);
  - учитель — ученики классов из `teacher_classes` (по `students.class_name`);
  - ученик — `{user.student_id}`.
- `allowed_pages(user, pages)`:
  - ученик — `portrait` и `practice`, если она есть в списке;
  - учитель — все страницы;
  - администратор — все.
  
  Содержимое `manage` зависит от роли — см. Z7.
- `ensure_demo_users(conn)`:
  - демо-учитель, привязанный к классу `seed.CLASS_NAME`;
  - демо-ученик, привязанный к Айгерим;
  - паролей в коде нет: они берутся из `PORTRET_DEMO_PASSWORD` или генерируются случайно (демо-вход — кнопкой, см. Z2);
  - администратор создаётся из `PORTRET_ADMIN_LOGIN` и `PORTRET_ADMIN_PASSWORD`, если они заданы.

### Z2. Вход — `ui/login.py`, функция `gate(conn, L) -> user`

- При `PORTRET_AUTH=off` возвращает псевдо-администратора: для локальной разработки, демо работает как раньше.
- Сессия хранится в `st.session_state["user"]`; тайм-аут неактивности — 60 минут.
- Форма входа на двух языках.
- Если `PORTRET_DEMO` не равна `0`, показываются кнопки «Войти как демо-учитель» и «Войти как демо-ученик» с пояснением «синтетический класс, настоящих данных нет».
- В боковой панели — имя и роль пользователя и кнопка «Выйти».
- После 5 неудачных попыток за 10 минут — пауза; хранить счётчик в памяти процесса достаточно.

### Z4. Согласие — `core/consent.py`

### Z6. Удаление данных ученика — `core/privacy.py`

`delete_student(conn, student_id)`:
1. Найди все таблицы (`sqlite_master`) со столбцом `student_id` или `submission_id` (`PRAGMA table_info`) и удали строки этого ученика и строки его работ.
2. Затем пройди по столбцам `observation_id`, `session_id`, `item_id`: удали строки, которые ссылаются на уже удалённые строки таблиц `observations`, `practice_sessions`, `practice_items`, если такие таблицы есть.
3. Удали `submissions` и `students`; отвяжи `users.student_id`.
4. Запиши в аудит только факт удаления и id.

Так удаление автоматически покрывает таблицы других направлений: тренажёр, отметки учителя, интервенции, распознавания.

## Этап C — PostgreSQL

Только после слияния остальных направлений: этот этап затрагивает все SQL-запросы.

- `db.connect()` выбирает SQLite или PostgreSQL по переменной `DATABASE_URL`. Обёртка переводит `?` → `%s` и отдаёт строки как `dict`.
- Вставка с получением id — `INSERT … RETURNING id` через помощник `db.insert(conn, table, **fields)`; заменить `cur.lastrowid` во всём коде.
- Схемы всех модулей (`ensure_schema`) приведены к SQL, совместимому с обеими базами.
- Тесты гоняются на обеих базах; если PostgreSQL недоступен — пропуск.

## Тесты — `tests/test_zeta.py`

- **Хэши:** хэш не равен паролю; проверка проходит для верного пароля и не проходит для неверного; у одинаковых паролей разные соли.
- **`authenticate`:** одинаковый ответ для неизвестного логина и неверного пароля; `disabled` — отказ.
- **Изоляция:**
  - два учителя с разными классами — пересечение видимых учеников пустое;
  - ученик видит только себя;
  - `allowed_pages` по ролям;
  - `class_map(..., student_ids=…)` фильтрует, а при `None` результат прежний.
- **`required_ok`:** синтетический ученик — да; новый ученик без согласия — нет; после отзыва — нет.
- **Аудит:** записи создаются, в тексте нет псевдонимов.
- **`delete_student`:** удаляет строки во всех таблицах, включая созданную прямо в тесте таблицу со столбцом `student_id` и таблицу со столбцом `observation_id`.
- **`export_class_csv`:** колонки и кодировка.
