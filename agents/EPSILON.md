# Агент Эпсилон · Учитель в контуре

Ты — агент **Эпсилон**. Любой вывод портрета должен быть опровержим, а система должна учиться на опровержениях.

Сейчас учитель не может сказать «это не ошибка» или «это другая ошибка», а команда не знает, насколько правила точны на реальных работах. Твоё направление:
- даёт учителю отметку на каждом выводе;
- пересчитывает портрет с учётом отметок;
- добавляет страницу «Качество»: точность каждого правила и экономию времени — цифры для слайда.

**Кратко**

- **Результат:** отметки «верно / неверно / другой тег» на выводах; портрет учитывает отметки; страница «Качество»; замер времени проверки.
- **Объём:** этап A — примерно 2–3 часа, этап B — 2–3 часа.
- **Зависимости:** нет.

## Общее для всех агентов

> Этот раздел одинаковый во всех шести заданиях: Альфа, Бета, Гамма, Дельта, Эпсилон, Дзета. Вы работаете параллельно в одном репозитории, каждый в своей ветке.

### Проект

**Портрет ученика** — MVP команды на хакатоне VENTUREHACK 2026, трек «Образование». Веб-приложение для учителя математики на Streamlit. Автопроверка домашних работ по алгебре 7–9 классов (SymPy) записывает в *журнал наблюдений* ошибки, способы решения и привычки ученика. Из журнала и комментариев учителя собирается *портрет* «где слаб и как работать» и *карта класса*. Интерфейс на русском и казахском.

Репозиторий: https://github.com/SatbayevAman/venture-hack. Подробности — в `README.md`.

### Принципы — нарушать нельзя

1. **Модель только на входе и на выходе.** Языковая модель распознаёт почерк, размечает свободный текст учителя и переформулирует готовые советы. Всё, что считает и решает, — обычный код, поэтому любой вывод воспроизводим.
2. **Только словарь тегов.** Выводы об ученике — только коды из `core/tags.py`. Неизвестный тег `db.add_observation` превращает в `other` или `teacher_other`. Новый вид вывода — это новый тег в словаре: название, совет учителю и совет ученику на `ru` и `kk`.
3. **Доказательство у каждого вывода:** работа, задача, строка, цитата. Меньше 3 случаев — пометка «мало данных» вместо вывода.
4. **Тон.** Описываем действия («в 4 работах из 6 нет проверки»), а не характер. Наводящий вопрос никогда не называет ответ. Версия для ученика — мягкая.
5. **Приватность.** Псевдонимы вместо имён. Фото не сохраняются — только строки текста. Синтетические данные везде подписаны как синтетические.
6. **Без ключа API всё работает.** Новая функция с языковой моделью обязана иметь офлайн-путь или аккуратно отключаться с объяснением.
7. **Два языка.** Каждая строка интерфейса — через `L("рус", "қаз")`, в словарях — поля `ru` и `kk`. Все новые казахские тексты перечисли в отчёте: их вычитает носитель языка.

### База и журнал

Таблицы в `core/db.py`: `students`, `assignments`, `problems`, `submissions` (`source`: `synthetic` или `live`), `attempts`, `steps`, **`observations`**, `teacher_comments`, `tags`. Портрет нигде не хранится: он каждый раз считается заново из `observations`.

Одна строка журнала — это контракт между проверкой и портретом:

```json
{"student_id": 1, "submission_id": 42, "problem_id": 27, "line_no": 1, "kind": "error",
 "tag": "lost_root", "skill": "quadratic", "evidence": "x² = 7x  →  x = 7",
 "detail": {"f": "x", "division": true}, "source": "auto", "confidence": 0.9}
```

Поля и смысл существующих значений не меняются. Новые значения `source` допустимы (например, `practice`): `portrait.build` учитывает только `auto` и `teacher`, поэтому числа портрета от них не меняются.

1. Ветка `agent/<имя>` от свежего `main`, небольшие осмысленные коммиты. Порядок: этап A целиком → все тесты проходят → PR; этап B — следующими коммитами после него.
2. Свой код — в своих новых файлах (см. раздел «Границы»). В общих файлах — только точечные вставки в указанных местах. Не переформатируй, не переименовывай и не переноси чужой код.

4. Новые таблицы — не в `db.SCHEMA`, а в своём модуле: константа `SCHEMA` и функция `ensure_schema(conn)` с `CREATE TABLE IF NOT EXISTS`. Твой код вызывает её перед обращением к таблице. Существующие таблицы не меняй, никаких `ALTER TABLE`.
5. Страница интерфейса — модуль `ui/<имя>.py` с функцией `render(...)`. `ui/__init__.py` — пустой файл; если его ещё нет, создай пустым. В `app.py` добавляются только импорт, ключ в `PAGES`, подпись в `PAGE_NAMES` и запись в словаре страниц в последней строке.
6. Новые зависимости — только если без них никак: строкой в `requirements.txt` с комментарием и с объяснением в отчёте. Python 3.9+: `from __future__ import annotations`, без `match`.
7. Тесты — в `tests/test_<имя>.py`, без сети и без ключа API (языковую модель подменяй через `monkeypatch`). Существующие тесты не правь.
8. `README.md` не трогай. Описание своей работы — в `docs/<имя>.md`; ссылку в README добавит человек при слиянии.
9. Конфликты при слиянии ожидаются только в местах регистрации: импорты в начале `app.py`, `PAGES`, `PAGE_NAMES`, словарь страниц в последней строке `app.py`, блоки словаря `TAGS`. Они аддитивны: оставляй обе стороны.

## Этап A — обязательный минимум

### E1. Отметки — `core/review.py`

```sql
CREATE TABLE IF NOT EXISTS reviews (
    id INTEGER PRIMARY KEY,
    observation_id INTEGER NOT NULL,
    verdict TEXT NOT NULL CHECK (verdict IN ('confirm', 'reject', 'retag')),
    new_tag TEXT,
    comment TEXT,
    reviewer TEXT,
    created_at TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS reviews_obs ON reviews(observation_id);
```

Функции:
- `ensure_schema(conn)`.
- `add(conn, observation_id, verdict, new_tag=None, comment=None, reviewer=None)`. `new_tag` — только тег из `T.TAGS` того же вида (`kind`), иначе `ValueError`.
- `latest(conn, ids) -> dict[int, row]` — последняя отметка побеждает.
- `apply(conn, rows) -> rows`:
  - наблюдения с последней отметкой `reject` удаляются из списка;
  - для `retag` подменяется `tag`, исходный сохраняется в `orig_tag`;
  - для `confirm` ставится `reviewed = "confirm"`;
  - без отметок строки возвращаются без изменений;
  - сам вызывает `ensure_schema`: на свежей базе таблицы ещё нет;
  - делает один запрос на всю пачку наблюдений, а не по одному.

### E2. Портрет учитывает отметки

- `portrait._obs`: после запроса — `rows = review.apply(conn, rows)`.
- `portrait._ref`: добавить `"obs_id": o["id"]`.

### E3. Элементы интерфейса — `ui/review.py`

- `controls(conn, obs_id, L, key)`:
  - три кнопки: «✓ верно», «✗ неверно», «↻ другой тег» (с выбором тега того же вида);
  - необязательный комментарий;
  - текущая отметка — бейджем;
  - после нажатия — `st.rerun()`, портрет пересчитается.
- `precision_badge(conn, tag, L) -> str` — HTML-бейдж «требует проверки» или пустая строка; используй существующие CSS-классы `badge b-low`.

### E4. Встраивание

Места вставки — в разделе «Границы». Отметки ставятся только на наблюдения с `source = "auto"`.

### E5. Страница «📈 Качество»

Функция `ui/review.py: render_quality(conn, L, lang, esc)` и логика в `core/quality.py`:
1. `tag_precision(conn) -> list[dict]`. По каждому тегу:
   - сколько отмечено, сколько «верно», «неверно», «другой тег»;
   - точность = верно / отмечено;
   - самая частая замена;
   - статус «требует проверки» при точности ниже 0.8 и не меньше 5 отметках.
2. `eval_accuracy(path="eval/labels.csv")` — прогон `checker.check_problem` по эталонным строкам: доля совпавших первых ошибок по строке и по строке с тегом. Если файла нет — пояснение, как его заполнить, со ссылкой на `eval/README.md`.
3. Время проверки — шаг E6.
4. Кнопка «Скачать метрики» — CSV или markdown для слайда.

Регистрация: `"quality"` в `PAGES` перед `"about"`; в `PAGE_NAMES` — `L("📈 Качество", "📈 Сапа")`; запись в словаре последней строки.

### E6. Время проверки — `core/quality.py`

```sql
CREATE TABLE IF NOT EXISTS check_timings (
    id INTEGER PRIMARY KEY,

    student_id INTEGER,
    seconds REAL NOT NULL,
    n_problems INTEGER,
    n_lines INTEGER,
```

- Функции `record_timing(...)` и `timing_summary(conn)`: медиана секунд и число работ.
- Настройка `manual_minutes_per_work`: учитель вводит её на странице «Качество» — «Сколько минут у вас уходит на проверку одной такой работы вручную?». По умолчанию пусто. Без неё экономию времени не показывать и ничего не выдумывать.

## Этап B — полная версия

- **B1. Отметки комментариев учителя:** учитель может снять неверно распознанный тег из своего комментария (важно, когда разметку делала модель).
- **B2. Кандидаты на исправление правил.** Для тегов со статусом «требует проверки» — список отклонённых случаев с доказательствами и кнопка «Скачать как markdown». Это материал для доработки правил агентом Бетой.
- **B3. Похожесть портрета.** Форма на портрете: «Похоже ли это на ученика? 1–5» и «какие пункты неверны» → своя таблица; на странице «Качество» — среднее и число оценок. Это напрямую закрывает шаг валидации «Похожесть портрета» из плана.
- **B4. «Это не ошибка» до записи.** На экране проверки у первой ошибки — кнопка «Это не ошибка»: работа всё равно записывается в журнал, но сразу с отметкой `reject`.

## Как это выглядит на демо

1. Учитель открывает доказательства «потери корня» и на одной работе нажимает «✗ неверно».
2. Портрет пересчитан: «в 3 работах из 6».
3. Страница «Качество»: «lost_root: N отметок, точность X %»; «медиана T с на работу против M мин вручную (по опросу)». Числа — только настоящие, из отметок и замеров.

## Подводные камни

- `portrait.build` вызывается для каждого ученика на карте класса, поэтому `apply` должен делать один запрос на пачку наблюдений.
- Отметка — это данные учителя: храни, кто и когда её поставил. Поле `reviewer` позже заполнит Дзета из аккаунта; пока пиши «учитель».
- Тег из отметки проходит ту же проверку словаря, что и все остальные теги.
